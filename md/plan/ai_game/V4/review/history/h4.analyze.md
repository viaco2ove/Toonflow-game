# h4 分析：挖矿小游戏没有进行下去

## 问题描述
用户通过 `#挖矿` 成功启动挖矿小游戏（返回 `on_mini_game_start`）后，输入"挖"无法被小游戏回合处理，而是走到了普通剧情流程（事件进度检测、章节判定、记忆刷新）。

## 日志关键线索

### 成功启动小游戏（第一次 `#挖矿`）
```
[2026-05-06 09:33:51] [story:event_progress:runtime]
recentDialogue[4] = { role:"旁白", eventType:"on_mini_game_start", content:"挖矿开始了。..." }
```
说明 `#挖矿` 成功触发 `handleMiniGameTurn`，rulebook.setup 正确执行，`on_mini_game_start` 正常返回。

### 小游戏启动后输入"挖"，走到普通流程（异常）
```
[2026-05-06 09:33:45.608] [game:orchestrator:key_nodes] {"node":"storyEventProgressModel:invoke:start",...}
[2026-05-06 09:33:51.421] [game:orchestrator:key_nodes] {"node":"storyEventProgressModel:invoke:done",...}
```
- `storyEventProgressModel` 是普通剧情流程的 AI 调用，**不是**小游戏流程
- 这说明 `handleMiniGameTurn` 对"挖"的输入返回了 `null`（未拦截），导致 `addSessionMessage` 走到了后续普通流程

### 后续多次"挖"都是同样问题
日志中所有"挖"消息（共4次）都走了普通流程，说明小游戏活跃状态没有被正确识别。

## 根因分析

### 假设1：`isMiniGameActiveState(state)` 返回了 `false`

**判定逻辑**（`MiniGameController.ts:252-256`）：
```typescript
export function isMiniGameActiveState(state: JsonRecord): boolean {
  const session = asRecord(asRecord(state.miniGame).session);
  const status = scalarText(session.status) as MiniGameStatus;
  return activeStatuses().has(status);  // ["preparing", "active", "settling", "suspended"]
}
```

**关键问题**：`addSessionMessage` 在 `#挖矿` 处理后，是否真的把更新后的 state（包含 `miniGame.session.status = "active"`）保存到了数据库？

### 假设2：`addSessionMessage` 中 state 保存时机问题

**`addSessionMessage` 流程**（`SessionService.ts:1429-1565`）：

1. **Line 1391**：插入用户消息到 `t_sessionMessage`
2. **Line 1429-1441**：调用 `handleMiniGameTurn`，若拦截则进入小游戏分支
3. **Line 1442-1542**：小游戏拦截分支
   - 若有 `pendingNarrativePlan`：写入 state
   - 若无：调用 `allowPlayerTurn`，插入小游戏消息到 `t_sessionMessage`
4. **Line 1503-1509**：**保存 state 到数据库**
   ```typescript
   const stateJson = toJsonText(state, {});
   await db("t_gameSession").where({ sessionId }).update({
     stateJson,
     chapterId: prevChapterId,
     status: prevStatus,
     updateTime: now,
   });
   ```
5. **Line 1543**：return 结果

**问题**：若 `miniGameResult.intercepted = true` 且走的是 `else` 分支（无 `pendingNarrativePlan`），代码会插入小游戏消息到 `t_sessionMessage`，**然后继续走到 1503 行保存 state**。

但这里有一个**关键疑点**：`handleMiniGameTurn` 中的 `root` 引用和 `addSessionMessage` 中的 `state` 是否是同一个对象？

### 假设3：对象引用不一致导致 state 未正确更新

**`handleMiniGameTurn` 内部**（`MiniGameController.ts:4934-5528`）：

```typescript
// Line 4936
const root = ensureMiniGameRoot(state);  // root = state.miniGame

// Line 5001（#挖矿 触发时）
root.session = session;  // state.miniGame.session = session
root.rulebook = { ... };
```

**`ensureMiniGameRoot`** 应该返回 `state.miniGame` 的引用。如果该函数返回的是**新对象**而非 `state.miniGame` 的引用，则 `root.session = session` 不会反映到 `state` 上。

**需要检查 `ensureMiniGameRoot` 的实现**！

### 假设4：`normalizeActionId("挖", options)` 返回了 null

**`miningOptions`**（`MiniGameController.ts:3852-3871`）：
```typescript
{ action_id: "excavate", label: "开采", aliases: ["挖矿", "挖掘"] },
{ action_id: "careful_excavate", label: "精挖", aliases: ["精细开采", "慢慢挖"] },
```

**`normalizeActionId`**（`MiniGameController.ts:4840-4866`）的匹配逻辑：
1. **精确匹配**：`text === item.action_id || text === item.label` → "挖" 不匹配任何
2. **别名匹配**：`text.includes(alias) || alias.includes(text)` → "挖".includes("挖矿") = false
3. **模糊匹配**：`item.label.includes(text) || text.includes(item.action_id)` → **"精挖".includes("挖") = TRUE**

所以 `normalizeActionId("挖", miningOptions)` **应该**返回 `"careful_excavate"`。

若确实返回了 actionId，则代码会走到 `miningStep(activeSession, actionId, input)`，小游戏应该正常推进。

**但是**——若 `isMiniGameActiveState(state)` 返回 `false`，则 `handleMiniGameTurn` 根本不会进入活跃小游戏的处理分支，而是走到 `detectGameTrigger`，返回 `null`。

## 根因确认（代码分析）

### 问题定位：`normalizeSessionState` 未显式处理 `miniGame`

**文件**：`src/lib/gameEngine.ts` (line 2098-2180)

`normalizeSessionState` 的返回值：
```typescript
return {
  ...base,              // ← 若 base.miniGame 存在，则会包含 miniGame
  version: 1,
  worldId,
  // ... 显式声明的字段（无 miniGame）
  // 没有 miniGame: ... 的显式声明
};
```

**问题**：
1. `...base` 展开会保留 `base.miniGame`（若存在）
2. 但若 `base.miniGame` 为 `undefined`，则展开后 `state.miniGame` 也会是 `undefined`
3. `gameEngine.ts` 中没有任何对 `miniGame` 的引用（已确认 grep 无结果）
4. 这意味着 `normalizeSessionState` **完全依赖** `...base` 展开来保留 `miniGame`

## 修复方案

### 方案1：在 `normalizeSessionState` 中显式保留 `miniGame`（推荐）

**文件**：`src/lib/gameEngine.ts`

在 return 对象中添加 `miniGame` 字段：
```typescript
return {
  ...base,
  version: 1,
  worldId,
  // ... 其他字段 ...
  
  // 显式保留小游戏状态，避免 ...base 展开时丢失
  miniGame: base.miniGame ? { ...base.miniGame } : ensureMiniGameRoot(base),
};
```

**注意**：`ensureMiniGameRoot` 在 `MiniGameController.ts` 中定义，需要调整导入或在 `gameEngine.ts` 中实现类似逻辑。

### 方案2：在 `addSessionMessage` 中手动恢复 `miniGame`

**文件**：`src/modules/game-runtime/services/SessionService.ts`

在 `normalizeSessionState` 调用之后，手动恢复 `miniGame`：

const state = normalizeSessionState(...);

## 附录：完整调用链

```
用户发送 "#挖矿"
  → addSessionMessage()
    → normalizeSessionState(sessionRow.stateJson, ...)  // 第一次，可能无 miniGame
    → handleMiniGameTurn({ state, ... })
      → ensureMiniGameRoot(state)  // 创建 state.miniGame = {}
      → isMiniGameActiveState(state)  // false（首次）
      → detectGameTrigger(...)  // 检测到 #挖矿
      → rulebook.setup(...)  // 创建 session，status = "active"
      → root.session = session  // state.miniGame.session = session
      → return { intercepted: true, ... }
    → 保存 state 到 DB  // state.miniGame 现在有值了
    
用户发送 "挖"
  → addSessionMessage()
    → normalizeSessionState(sessionRow.stateJson, ...)  // 第二次，从 DB 读取
      → base = parseJsonSafe(stateJson, {})
      → base.miniGame 应该存在（因为第一次调用已保存）
      → return { ...base, ... }  // 若 base.miniGame 存在，则 state.miniGame 存在
    → handleMiniGameTurn({ state, ... })
      → isMiniGameActiveState(state)  // 应为 true
      → normalizeActionId("挖", options)  // 应返回 "careful_excavate" 或 "excavate"
      → rulebook.applyAction(...)  // miningStep(...)
      → return { intercepted: true, ... }
```

**关键点**：若 `normalizeSessionState` 的返回值中缺少 `miniGame`，则第二次调用时 `isMiniGameActiveState(state)` 返回 `false`，导致 `handleMiniGameTurn` 返回 `null`（未拦截）。
