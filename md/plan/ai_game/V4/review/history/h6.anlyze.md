# h6 问题分析与解决方案

> 对应需求：h6.md 要求的挖矿小游戏正确流程  
> 对应日志：logs/event_log/app-2026-05-07.mini_game.summary.md、logs/app-2026-05-07.02.log  
> 对应截图：用户输入 #挖矿 -> 旁白硬编码开场 -> 用户输入 美杜莎陪练，挖金矿 -> 旁白错误输出主线台词，同时左下角仍显示 挖矿 第1轮 - survey

---

## 一、现象还原（按时间线）

### 1. 点击回溯后的状态
会话历史里已经存在两条小游戏记录：
- eventType: on_mini_game_abort —— "你已强制退出 挖矿..."
- eventType: on_mini_game_start —— "挖矿开始了。你准备挖什么矿物？..."

这说明用户点击回溯后，前端重新加载了会话，但后端没有把叙事上下文切回小游戏模式，主线剧情的 pendingNarrativePlan（萧炎问你要不要跟上他）仍然存活。

### 2. 用户输入 #挖矿（addMessage 入口）
story:mini_game:agent 拦截日志显示：
- eventType: on_mini_game_start
- gameType: "未知"（本应识别为 mining）
- motive 直接等于硬编码旁白文案

addMessage 直接返回了旁白文案，响应体高达 100KB（内含完整历史）。没有调用 /game/streamlines 生成台词，也没有调用 /game/streamvoice 预热语音。story:orchestrator:runtime 判断 "不走到模型。原因：pendingNarrativePlan_exists"，planRole: "用户"。

### 3. 用户输入 美杜莎陪练，挖金矿
story:mini_game:runtime 正确解析出 actionId: "mentor:美杜莎"、targetName: "金矿"。大模型生成了美杜莎陪练台词。但紧接着 story:orchestrator:runtime 再次因为 pendingNarrativePlan_exists 判断不走模型。

### 4. /game/streamlines 被调用，但上下文完全错误
streamlines 收到的 [当前事件] 仍然是主线 index:6（萧炎问你要不要跟上他）。虽然 [本轮动机] 是 "挖矿：美杜莎加入协助"，但发言器基于错误的当前事件，生成了主线台词：

> (乌坦城的风裹挟着淡淡的药草香掠过青石板路，远处萧家府邸的旗杆依旧猎猎作响。)真正的世界，才刚刚开始。萧炎已经踏上王者之路，你要——跟上他吗？

该错误台词随后走了 /game/streamvoice -> /voice/audioProxy 完成语音播放。前端状态与后端台词严重错位：界面左下角显示 挖矿 第1轮 - survey，用户听到的却是主线剧情。

## 二、根因分析

### 根因 1：addMessage 在 #挖矿 入口直接硬编码返回旁白，跳过编排-发言-语音链路
h6.md 明确要求：addMessage 不再直接生成旁白台词。正确流程应该是 addMessage 只做状态标记，随后由编排通道生成旁白播报并走语音。

当前代码把开场文案直接当成响应内容塞回前端，导致：
- 没有走 /game/orchestration/minigame -> /game/streamlines -> /game/streamvoice 的标准链路
- 没有真正创建小游戏的叙事计划（pendingMiniGamePlan）

### 根因 2：小游戏没有独立的事件上下文，streamlines 始终读取主线 current_event
无论 activeMiniGame 是否存在，/game/streamlines 在生成台词时，仍然使用主线章节里的 current_event（index:6）。小游戏模式下，旁白/陪练的发言需要基于小游戏回合上下文，而不是主线场景事件。

架构上缺少一个机制：在小游戏 active 期间，临时把 streamlines 的上下文替换为小游戏上下文，或向 prompt 注入小游戏专属事件摘要。

### 根因 3：主线 pendingNarrativePlan 阻塞了小游戏编排
story:orchestrator:runtime 两次出现 pendingNarrativePlan_exists，导致编排器拒绝为当前用户输入调用大模型。这意味着主线叙事计划与小游戏计划共存且冲突。小游戏被拦截后，编排器仍然被主线未完成的 plan 卡住。

小游戏开始时应挂起或重置主线的 pending plan，或者小游戏编排走独立分支，不受主线 plan 影响。

### 根因 4：点击回溯后未正确恢复小游戏叙事上下文
回溯功能重新加载了历史对话，但后端仅恢复了对话列表，没有根据历史恢复小游戏运行态（gameType、phase、status）。结果：前端通过历史记录认为自己回到了小游戏，后端编排器却按主线逻辑执行。

### 根因 5：陪练台词缺少独立的语音链路
美杜莎的陪练台词虽然由大模型生成了，但日志中没有看到 /game/streamvoice 调用该台词的记录。当前似乎只有旁白台词走了语音，陪练台词可能仅在 addMessage 响应中以文本形式返回，缺少语音播放。

## 三、解决方案

### 方案 1：重构 #挖矿 入口流程（addMessage）
- 禁止 addMessage 直接返回旁白文案
- 用户输入 #挖矿 后，addMessage 仅做以下事情：
  1. 初始化/恢复小游戏状态：gameType: mining，phase: survey，status: active，round: 1
  2. 向会话历史插入一条轻量级事件标记（如 on_mini_game_enter），不包含大段旁白文本
  3. 创建一个小游戏的 pendingPlan，事件类型为 on_mini_game_broadcast（播报回合：规则说明）
  4. 返回响应，告知前端已进入小游戏模式，等待下游语音推送
- 旁白的规则说明台词，必须由 /game/streamlines 生成，并走完整的 /game/streamvoice 语音链路

### 方案 2：为 streamlines 提供小游戏上下文隔离
- 在 /game/streamlines 处理逻辑中增加判断：
  - 如果当前会话存在 activeMiniGame 且 status 为 active，则优先使用小游戏提供的上下文
  - 向 prompt 注入 miniGameContext：gameType、phase、round、motive、currentEventSummary（小游戏虚拟事件摘要）
  - 屏蔽或降级主线 current_event，避免发言器被主线事件污染
- 或者：小游戏模式下，编排器临时构造一个虚拟的 miniGameEvent 并设为 current_event，使 streamlines 无感知切换

### 方案 3：小游戏编排器与主线编排器解耦
- 当小游戏处于 active 状态时，/game/orchestration/minigame 应拥有更高优先级
- 小游戏拦截成功后，挂起（suspend）主线的 pendingNarrativePlan，而不是让它继续阻塞 story:orchestrator:runtime
- 小游戏结束（#退出、矿洞倒塌、矿物清空）后，再恢复主线的 pending plan，或根据当前主线事件重新生成 plan
- 确保 story:orchestrator:runtime 在小游戏 active 期间，不会因为 pendingNarrativePlan_exists 而跳过小游戏编排

### 方案 4：修复点击回溯的状态恢复
- 在回溯/重载会话历史时，后端增加 recoverMiniGameState 逻辑：
  1. 扫描历史消息中最后一个小游戏相关事件
  2. 如果最后一条是 start 或 on_mini_game（且无对应的 end/abort 在其后），则恢复小游戏状态到数据库/缓存中的最新快照
  3. 若回溯点恰好处于小游戏进行中，重新进入播报回合（或根据保存的 phase 恢复），确保前后端状态一致
  4. 前端回溯时，同样需要识别历史中的小游戏标记，恢复小游戏 UI 面板状态

### 方案 5：补齐陪练回合的完整语音链路
- 用户动作解析完成后（如选定美杜莎、执行开采），如果需要陪练发言：
  1. 大模型生成陪练台词（已有）
  2. 将陪练台词推入 /game/streamlines（speaker 为该陪练角色，如美杜莎）
  3. /game/streamlines 返回台词后，调用 /game/streamvoice 预热该角色语音
  4. 前端通过 /voice/audioProxy 播放
- 确保陪练台词和旁白播报台词分别独立走完整的语音链路，不要合并到一次 addMessage 响应里

### 方案 6：明确回合推进顺序
按照 h6.md 要求，严格实现以下循环：

```
[进入] 用户输入 #挖矿
   |
[播报回合] 旁白：规则说明（走 orchestration -> streamlines -> streamvoice）
   |
[用户回合] 用户输入动作（如：美杜莎陪练，挖金矿）
   |
[动作解析] mini_game runtime 解析 action_id / target_name
   |
[陪练回合] 如有陪练，陪练发言（走 streamlines -> streamvoice）
   |
[行为结算] 旁白播报：挖矿结果、奖励、剩余矿物（走 streamlines -> streamvoice）
   |
[奖励生效] 物品立即写入用户物品栏
   |
循环回到 [用户回合]
   |
[结束] #退出 / 矿物清空 / 矿洞倒塌
   |
[恢复主线] 恢复主线 pending plan，继续主线剧情
```

## 四、验证标准（修复后需检查）

1. 用户输入 #挖矿 后，addMessage 响应中不包含大段旁白文本，仅返回状态标记和前端需要的小游戏面板数据
2. DevTools Network 中可见：/game/orchestration/minigame（编排）、/game/streamlines（生成旁白规则说明）、/game/streamvoice（预热语音）、/voice/audioProxy（播放语音），且台词内容必须是挖矿规则/场景相关，不能出现主线剧情（如萧炎）
3. 用户输入动作后，陪练台词（如美杜莎）也有独立的 /game/streamvoice + /voice/audioProxy 调用
4. 点击回溯到小游戏进行中时，旁白再次播报当前回合状态（或规则摘要），而不是跳到主线事件
5. story:orchestrator:runtime 在小游戏 active 期间不再报 pendingNarrativePlan_exists 阻塞
6. story:mini_game:agent 在 #挖矿 入口识别的 gameType 必须是 "mining"，不能是 "未知"
