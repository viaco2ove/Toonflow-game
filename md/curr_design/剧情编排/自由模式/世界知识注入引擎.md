### 整体判断

方案1 格式专业，但**直接照搬酒馆全套字段对当前项目过度设计，且有架构隐患**。建议方案2 大幅精简后再做，且时序上排在 P1 之后。

### 一、会打架的字段（危险）

- **`probability` 控时序 vs 章节状态机**：方案1 用 `probability:0` 控制"后期角色前期不登场"。但角色登场时机本应由章节状态机的 `phase` / `allowedSpeakers` 管。两套时序并存必冲突：章节推进了但概率还是 0（忘改）、或概率变 100 但章节没到。
- **`order` 分层 vs 结构化分区**：酒馆用 order 控注入位置，因为它只有一条扁平管道。本项目 `buildOrchestratorPromptPayload` 已是结构化分区（世界/章节/角色/事件/回合）。再叠 order 排序，语义混乱。
- **`group` 互斥**：25~30 条目规模，互斥场景极少，可用 `category` + 简单规则替代。

### 二、重复的字段（冗余，违反单一数据源）

| 世界书类目 | 已有等价物 | 冲突 |
|---|---|---|
| `characters` | NPC 参数卡 `parameterCardJson` | 同一 NPC 设定存两份，谁更新？编排师看哪个？ |
| `items` | 玩家/NPC 参数卡 `items` | 同上 |
| `factions` | `worldGlobalBackground` 势力设定 | 同上 |
| `constants` 总纲 | `worldGlobalBackground` | 重复 |

最尖锐：`characters` 条目 vs NPC 参数卡，直接违反 P0 方案确立的"单一数据源"原则。

### 三、方案2 保留的字段（精简到 5 个）

`title` / `category` / `keys` / `constant` / `content`。`probability` **仅 `random` 类目保留**，其余删除。砍掉 `selectiveLogic` / `selectiveKeys` / `group` / `order` 分层。`category` 只保留参数卡覆盖不了的：`locations` / `events` / `world` / `random`（角色/物品/势力用参数卡，不进世界书）。

### 四、注入引擎三个待回答问题

1. **扫描什么**：应扫描编排师 payload 的 `recentDialogue` + `latestPlayerMessage`，不是原始消息表，否则数据通路与编排师脱节。
2. **token 预算**：2000 token 默认值必须与 `compact`/`advanced` 模式联动，compact 模式要更小，否则 compact 不 compact。
3. **与 `worldBreathing` 的关系（最关键）**：P0 的 `worldBreathing`（动态状态：时间/天气/NPC 活动）和 `worldKnowledge`（静态设定）应**合并成 payload 同一个 `worldContext` 区块**，而非各搞一套，否则编排师面对两个世界信息源不知谁优先。

### 五、时序建议：现在不做，排在 P1 之后

- P0 的 `worldBreathing` 已是一个（简陋的）世界知识注入（从 `dynamicWorldGlobalBackground` + `memoryFacts` 提取）。先看 P0 + P1 上线后自由模式够不够鲜活，不够再上世界书。
- 世界书解决"上下文装不下所有设定"，但本项目 25~30 条目规模，`worldGlobalBackground` + 参数卡可能已够。世界书为超大世界准备，当前世界可能不够大。
- **数据来源比引擎本身更棘手**：25~30 条目谁写？手填工作量巨大，AI 生成质量不可控。引擎建好数据是空的 = 白搭。

### 六、分阶段建议

- **阶段 1（现在）**：只定精简格式（5 字段），不写引擎。
- **阶段 2（P1 落地后）**：若发现地点氛围/事件背景等静态知识确实缺，再做注入。`keys` 匹配 `recentDialogue` + `latestPlayerMessage`；与 `worldBreathing` 合并成 `worldContext`；token 预算联动 compact/advanced；`category` 只留 `locations`/`events`/`world`/`random`。
  - **实现备注（2026-07-26）**：原设计仅自由模式注入，实测发现章节模式同样需要地点氛围/世界设定等静态知识，已扩展为**全模式注入**（章节+自由）。`worldBreathing`（时间/天气/NPC活动）仍仅自由模式，世界书注入与 worldBreathing 解耦。
- **阶段 3（真有需要时）**：`random` 类目多到需互斥控制，再补 `group`/`probability`。

 这是个"按需求紧迫度递增、按过度设计风险递减"的漏斗：
  阶段1: 格式+UI        ← 现在就要(让世界能填书)        低风险
  阶段2: 注入引擎        ← 等P1跑完看缺不缺(可能不做)    中风险(要解架构冲突)
  阶段3: 随机/互斥控制    ← 等random条目够多(大概率不做) 高风险(过度设计)

  阶段 1（现在）——只定格式，不写引擎

  - 做什么：只定精简到 5 字段的条目格式（title/category/keys/constant/content），加上世界书的增删改查 UI
  - 为什么停在这：因为当前世界不够大。文档第五节明说"本项目 25~30 条目规模，worldGlobalBackground +
  参数卡可能已够。世界书为超大世界准备"。引擎写好了，但世界书条目是空的，等于白搭。先把"容器"和"录入界面"做出来，让世界能往里填东西，等填到一定量再说注入。

  阶段 2（P1 落地后）——做注入引擎，但带触发条件

  - 做什么：keys 关键词匹配 + 扫描对话 + token 预算 + 和 worldBreathing 合并成 worldContext
  - 触发条件："若发现地点氛围/事件背景等静态知识确实缺" 才做。也就是要先用 P0+P1（世界呼吸 + NPC
  自主行为，刚做完的）跑一段时间，看自由模式到底够不够鲜活。如果够，世界书引擎可能根本不需要做。
  - 为什么不直接做：因为前面那几个打架/重复的字段问题（probability vs 状态机、order vs 结构化分区、characters vs
  参数卡）还没解干净，贸然做全套会和现有架构打架。等真需要了，需求也清楚了，再裁剪着做。

  阶段 3（真有需要时）——补随机/互斥控制

  - 做什么：random 类目多了，需要互斥（同组只触发一个）和概率控制时，再补 group/probability
  - 为什么放最后：文档第三节说"25~30 条目规模，互斥场景极少"。互斥是给"几十上百条 random 事件"准备的，当前规模用不到。属于过度设计，留到规模真到了再说。

## 测试
### p1 测试方法

  1. 新建/打开故事 -> 全局背景区看到「📖 世界书」按钮
  2. 点开 -> 弹窗显示条目列表（首次为空）
  3. 新增条目 -> 填表单 -> 保存 -> 列表刷新
  4. 导入 worldbook.json -> 选 replace 模式 -> 42 条全部导入
  5. 导出 -> 下载 worldbook.json -> 内容一致
  6. 切换故事 -> 世界书隔离
  7. 跨用户 -> 操作他人世界书返回 403

### p2 测试

> 阶段2 注入引擎：自由模式下，世界书条目按关键词匹配注入编排师上下文。
> 观察工具：ScenePlay 游玩页「激活的世界书（N）」面板（在"当前章节事件"按钮上方）。

**前置条件**
1. 故事已导入世界书条目（p1 已验证，world_id=41 有 47 条）
2. 进入该故事的**自由模式**章节（eventFlowType=free_runtime）
3. 后端服务已重启（加载阶段2 代码）

**测试用例**

1. **常驻条目恒定注入**
   - 操作：自由模式随便发一句话（如"看看周围"）
   - 预期：「激活的世界书」面板里至少有 6 条 constants 类目条目（世界总纲/财气眼/战斗公式/等级体系/主角规则/旁白规则），每条带绿色「常驻」标记
   - 验证点：无论用户说什么，这 6 条每轮都在
   - 日志：worldBook:injected

2. **关键词激活地点条目**
   - 操作：发"去黑风寨看看"或"回山寨"
   - 预期：面板出现「黑风寨」条目（locations 类目，蓝色标签），因为 keys 含"黑风寨/山寨/大当家"
   - 反例：发"去坊市逛街"不应激活黑风寨（keys 不匹配）

3. **关键词激活角色相关 world 条目**
   - 操作：发"和师妹聊聊"或"白锦儿在哪"
   - 预期：注意 characters 类目（白锦儿）**不会**出现（走参数卡不注入）；但「NPC关系网」(world 类目) 若 keys 命中"师妹"会出现

4. **characters/factions/items 不注入**
   - 操作：发"纯小白"或"主角"
   - 预期：「纯小白（主角）」characters 条目**不出现**（这些走参数卡），但 constants 里的「主角核心规则」会出现（因为它是 constant）

5. **token 预算截断（compact 模式）**
   - 操作：把编排模型切到 compact 模式，发一句命中很多关键词的话（如"黑风寨后山秘境坊市"）
   - 预期：面板条目数 < 全部匹配数（800 token 预算截断了低 order 条目）
   - 后端日志：`worldBook:injected` 节点看 matched 数 vs 实际注入数

6. **章节模式零回归**
   - 操作：切到章节模式（chapter_content 阶段）对话
   - 预期：「激活的世界书」面板显示"暂无激活条目"，worldContext 为 null
   - 验证点：章节模式完全不读世界书 DB、不注入

7. **正则 keys 匹配（如有）**
   - 操作：若有条目 keys 用 `/打[铁鍛]/`，发"去打铁"
   - 预期：该条目被激活；发"打猎"不激活（正则不匹配）

8. **DB 读失败兜底**
   - 操作（可选）：临时把 worldId 改错或清空 t_worldBook
   - 预期：编排不报错，面板空，日志有"预加载世界书失败"警告

**日志验证（后端 DebugLog）**
- `worldBook:injected`：记录 totalEntries（总条目数）/ matched（匹配数）/ tokenBudget / scanTextPreview（扫描文本预览）
- `runNarrativePlan:enter` -> `worldBook:injected` -> `storyOrchestratorModel:invoke` 顺序出现，说明预加载在编排前完成

**分页验证**
- 面板每页 5 条，超 5 条显示「第 X/Y 页」+ 上一页/下一页
- 每轮新编排结果自动回到第一页
