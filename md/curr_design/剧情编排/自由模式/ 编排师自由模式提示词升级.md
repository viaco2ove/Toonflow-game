# 编排师自由模式提示词升级（方案）

> 配套文档：`自由模式对比酒馆世界书.md`（分析对比）
> 本文聚焦「提示词升级」这一个具体动作，给出落地方案。
> 结论先行：**不独立做第三套 system prompt，在现有 compact / advanced 两套上加条件段 + payload 注入。**

---

## 一、现状分析（基于代码事实）

### 1.1 提示词的真实分层

编排师提示词由两个**正交维度**组成，文档 `自由模式对比酒馆世界书.md` 1.2 节那张对比表混淆了它们：

```
system prompt 层（2 套，按「速度 / 推理预算」分裂）
  ├─ story-orchestrator-compact    极简版（JSON 直出，偏向快速）
  └─ story-orchestrator-advanced   高级版（逐行字段，偏向质量）
        ↑ 这两套对 free / chapter 完全一视同仁

payload 数据层（按 free / chapter 分，靠字段值区分）
  ├─ chapter：chapterDirective 有内容、phaseGoal 具体事件、eventFlowType=chapter_content
  └─ free：   chapterDirective 空、phaseGoal="自由行动中…"、eventFlowType=free_runtime
```

**证据：**
- `src/lib/fixDB.prompts.ts` 中 `PROMPT_STORY_ORCHESTRATOR_COMPACT`（L856–991）与 `PROMPT_STORY_ORCHESTRATOR_ADVANCED`（L994–1201）**全文无 `free_runtime` 字样，无任何「自由模式」专属指令**。
- `src/modules/game-runtime/engines/NarrativeOrchestrator.ts` 的 `OrchestratorPromptPayload` 类型（L162–200）与 `buildOrchestratorPromptPayload` 负责灌值，自由模式贫乏是**这一层灌了空值**导致的，不是 system prompt 分裂。

### 1.2 自由模式现在为什么"贫乏"

自由模式下 payload 的实际取值：

| 字段 | 章节模式 | 自由模式 | 后果 |
|------|---------|---------|------|
| `currentEventSummary` | 具体事件摘要 | "自由行动中，等待承接用户的新动作" | AI 不知道当前在干什么 |
| `currentEventFacts` | 具体事实 | `["当前无进行中的任务","应根据用户最新输入继续自由剧情"]` | 没有锚点 |
| `chapterDirective` | 章节提纲 | 空字符串 | 没有剧情骨架 |
| `phaseAllowedSpeakers` | 受限角色 | 全部角色 | 角色无约束 |
| `currentEventFlowType` | `chapter_content` | `free_runtime` | 唯一的模式标记 |

**但 system prompt 层根本没有针对 `free_runtime` 做任何特殊引导。** AI 在自由模式下拿到的指令和章节模式完全一样，只是数据更空——所以它只能等用户输入驱动，世界是"静默"的。

### 1.3 compact 与 advanced 的重复度

对比两套 prompt，以下内容**逐字相同**：
- 角色选择规则、`@角色名：xxx` 优先级机制
- `turn_state` 各字段语义
- 记忆触发条件（`trigger_memory_agent`）
- 输出 JSON 结构
- "NPC 优先原则"、`.` 跳过指令

差异仅在：compact 直出 JSON，advanced 逐行字段 + 多一段「核心目标 / 关键原则」。**两套之间已存在维护隐患，再按 free/chapter 分裂会变成 4 套组合。**

## 二、为什么「不独立做第三套」

| 论点 | 说明 |
|------|------|
| **维度爆炸** | 现在按「速度」分 2 套。再按「模式」分 → 2×2=4 套（compact-free / compact-chapter / advanced-free / advanced-chapter），且 80% 文本重复，维护成本不可接受 |
| **能力同构** | 自由模式与章节模式的编排能力完全一样：选谁说话、推进一小步、`await_user`、`@角色名` 优先级、记忆触发。差异只在「内容生成倾向」（世界呼吸 / NPC 自主 / 叙事钩子） |
| **倾向是数据驱动，非指令驱动** | 给 AI 喂 `worldBreathing` 数据，它自然写氛围；只在 prompt 写「要有世界呼吸感」却不给数据，它就脑补 → 时间倒流、天气乱跳。文档第四层那六条规则本质是「通用追加指令」，不是一套新 prompt |

---

## 三、升级方案（两层）

### 层 A：system prompt 追加「自由模式规则」条件段（轻量，立即见效）

在 compact / advanced 两套 prompt 的**核心规则之后、输出格式之前**，追加一段模式开关：

```text
## 自由模式规则（当 current_event.flow = "free_runtime" 时生效）

自由模式下没有固定事件提纲，世界靠你主动呼吸。在遵守上述通用规则之外，额外做到：

1. 世界呼吸：根据 payload 中的 world_breathing（时间 / 天气 / 环境氛围 / NPC 活动）描述环境变化，不要凭空捏造时间或天气
2. NPC 自主性：NPC 应有独立于用户的行为与反应，不要只是「等待用户开口」
3. 叙事钩子：每 2~3 轮对话，可在本轮 motive 中植入一个可探索的线索（远处异响 / 陌生面孔 / NPC 主动搭话），但不要替用户做决定
4. 空间感：交代当前场景细节，让用户感到「身在此处」
5. 因果连贯：承接 recent_dialogue 与 memory，不前后矛盾
6. 不抢戏：用户始终是主角，世界只是背景板；NPC 推进一小步即停，把选择权留给用户

当 flow ≠ "free_runtime" 时，忽略本段，严格按事件提纲推进。
```

> 关键：第 1 条明确「不要凭空捏造时间或天气」，把不确定性约束在 payload 提供的数据内，避免脑补导致的时间倒流。

### 层 B：payload 注入 `worldBreathing`（中量，复用现有数据）

**不新建世界知识引擎**，先从已有的记忆数据里提取，验证效果：

```typescript
// NarrativeOrchestrator.ts · OrchestratorPromptPayload 新增字段
worldBreathing?: {
  timeOfDay?: string;      // 从 state.memoryFacts / dynamicWorldGlobalBackground 提取
  weather?: string;        // 同上
  ambientEvents?: string[];// 同上
  npcActivities?: { npc: string; activity: string }[];
}
```

数据来源优先级（**全部已有，零新建服务**）：
1. `state.dynamicWorldGlobalBackground`（记忆管理器每轮维护）——主要时间 / 天气 / 世界状态来源
2. `state.memoryFacts`——环境细节、NPC 近期行为
3. `state.vars.activeFreeTask`——若有进行中任务，作为 `npcActivities` 来源

注入位置：`buildOrchestratorPromptStats` / `buildCompactOrchestratorSections` 的「当前事件」块之后，新增「世界呼吸」块。

## 五、风险与边界

### 5.1 单改提示词治标不治本

层 A（提示词）见效快，但若不做层 B（数据），AI 会更努力地**编**——编出来的时间线前后矛盾。所以层 A、B 必须一起上，不能只做 A。

### 5.2 时间倒流的根因未解

`worldBreathing` 复用 `dynamicWorldGlobalBackground`，但它由记忆管理器每轮重写，**不是确定性的时间推进**。可能出现：
- 上一轮"黄昏"，这一轮"正午"（记忆管理器覆盖丢失）
- 天气随机跳变

**这是 P1 架构问题（世界 tick 机制），本文档不解决**，但层 A 的措辞（"不要凭空捏造时间或天气"）已把损害限制在 payload 提供的范围内。是否上 tick，观察上线后时间倒流频率再定。

### 5.3 与记忆管理器的边界

`dynamicWorldGlobalBackground` 已被记忆管理器（`PROMPT_STORY_MEMORY`）维护。`worldBreathing` 只是**编排师侧的只读消费**，不回写、不与记忆管理器抢职责。两者关系：

```
记忆管理器（每轮）→ 维护 dynamicWorldGlobalBackground（单一数据源）
                          ↓ 只读
              编排师 payload worldBreathing（展示用提取）
```

不要让编排师也维护世界状态，否则两处写、必冲突。

### 5.4 token 成本

`worldBreathing` 预估增加 80–150 字。compact 模式下可只取 `timeOfDay` + `weather` 两个字段压缩成一行，控制增量。

## 六、验证方法

1. **提示词体积**：观察 `story:orchestrator:stats` 日志，确认 free 模式 system_chars 增量在预期内（compact +约 200 字，advanced +约 220 字）
2. **世界呼吸是否生效**：自由模式下连续空转 5 轮（用户输入 `.`），检查编排师是否主动推进环境 / NPC，而非干等
3. **时间一致性**：连续 10 轮记录 `timeOfDay`，检查是否倒流
4. **不抢戏**：检查 NPC 推进后是否 `await_user=true`，没有连续编排多轮 NPC 把用户晾一边
5. **章节模式无回归**：章节模式下 `flow=chapter_content`，条件段应被忽略，行为与升级前一致

---

## 七、落地顺序

1. **先做层 A**（提示词追加）——立即可见，即使数据层未就绪也能看 AI 倾向变化
2. **再做层 B**（payload 注入）——让层 A 的指令有数据支撑
3. **观察 1 周**——收集时间倒流 / 角色抢戏 / 世界静止三类问题数据
4. **再决定**是否进入 P1（世界 tick / NPC 自主行为调度 / 世界知识注入引擎）

> P0 的两项（提示词升级 + 数据注入）是「用最小改动验证方向」，不是终点。世界书机制、tick、事件链是后续架构投入，依赖 P0 验证结果。
