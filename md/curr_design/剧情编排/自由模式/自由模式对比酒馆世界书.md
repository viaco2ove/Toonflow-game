## 一、当前自由模式的编排逻辑

### 1.1 什么是自由模式

自由模式在代码中称为 **"自由章节"（Free Chapter Runtime Mode）**：

```typescript
// gameEngine.ts
export function isFreeChapterRuntimeMode(chapter: any): boolean {
  // 同时没有 completionCondition 和 endingRules → 自由章节
  return !hasCompletionCondition && !hasEndingRules;
}
```

核心特征：**没有结束条件，没有下一章，静态事件耗尽后不断生成动态事件，永不结束**。

### 1.2 编排师在自由模式下看到什么

当前自由模式下，`buildOrchestratorPromptPayload` 做了**全面替换**：

| 字段 | 章节模式 | 自由模式 |
|------|---------|---------|
| phaseLabel | 具体阶段名 | `"自由剧情"` |
| eventSummary | 具体事件摘要 | `"自由行动中，等待承接用户的新动作。"` |
| eventFacts | 具体事件事实 | `["当前无进行中的任务", "应根据用户最新输入继续自由剧情"]` |
| phaseGoal | 具体阶段目标 | `"根据用户最新输入推进自由剧情。"` |
| chapterDirective | 章节提纲 | **空字符串** |
| chapterUserTurns | 用户交互节点 | **空字符串** |
| allowedSpeakers | 受限角色 | **全部角色** |
| eventFlowType | chapter_content | `"free_runtime"` |

**结论：编排师在自由模式下的上下文极度贫乏。** 它看到的只是一个"自由行动"的空壳，没有世界状态、没有 NPC 自主行为、没有任何动态注入——全靠用户输入驱动。

### 1.3 自由任务系统（唯一的亮点）

自由模式下有一个 `FreeChapterTaskService`，支持：
- 旁白推荐 1~5 个任务 → 用户选择 → AI 生成任务蓝图 → 创建动态事件
- 任务有过程、成功条件、失败条件
- 支持 `#任务:xxx` 直接创建任务
- 任务完成后发放经验/金币/物品奖励

但它的局限也很明显：**只在用户主动触发时才工作，世界本身是"静默"的。**

## 二、SillyTavern 世界书机制详解

### 2.1 核心概念

世界书（World Info / Lorebook）本质上是一个 **动态上下文注入引擎**：

```
用户输入 → 扫描聊天记录(可配置深度) → 匹配关键词 → 命中条目注入 prompt → AI 生成
```

### 2.2 条目结构

每条世界书条目包含：

| 字段 | 作用 |
|------|------|
| **Key（激活关键词）** | 支持纯文本 + 正则表达式，命中即激活 |
| **Content（内容）** | 激活后注入 prompt 的文本，需独立自描述 |
| **Order（插入顺序）** | 数值越大越靠后，对输出影响越大 |
| **Position（插入位置）** | Before/After角色定义、@深度、Author's Note 等 |
| **Probability（触发概率）** | 0~100%，可实现随机事件 |
| **Constant** | 始终激活（不依赖关键词） |
| **Selective Logic** | AND ANY / AND ALL / NOT ANY / NOT ALL 过滤 |
| **Inclusion Groups** | 同组多条目触发时只选一个（带权重随机） |
| **Recursive Scanning** | 条目内容中的关键词可触发其他条目 |

### 2.3 关键机制

**1) 递归激活**：条目 A 命中 → 注入内容 → 扫描 A 的内容 → 发现条目 B 的关键词 → 也注入 B

**2) 上下文预算**：所有激活条目有总 token 上限，按 Order 排序，超出预算的截断

**3) 多层级绑定**：
- 全局世界书（所有聊天生效）
- 角色专属书（跟角色走）
- 人设书（跟 User Persona 走）
- 单聊专属书（仅当前对话）

**4) 插入策略**：均匀排序 / 角色优先 / 全局优先

### 2.4 世界书解决的核心问题

世界书不是"让 AI 记住更多"，而是 **"在正确的时间，给 AI 正确的信息"**。它解决的是：

- 上下文窗口有限，不可能把所有世界观塞进去
- 不同场景需要不同的背景信息
- 世界应该"活"起来——不同地点、不同 NPC、不同时间，世界呈现不同面貌

## 三、能否接入世界书机制？

**可以，而且非常契合。** 但不需要照搬 SillyTavern 的实现，而是取其核心思想——**动态上下文注入**——融入 Toonflow 现有架构。

### 3.1 现有架构的优势

Toonflow 已经有很好的基础：

1. **`buildOrchestratorPromptPayload`** 是天然的世界书注入点——它已经负责构建编排师的上下文
2. **`memorySummary` / `memoryFacts`** 已经在做类似的事——动态世界背景
3. **世界/角色/章节数据** 已经结构化存储在数据库中
4. **状态机** 已经追踪了当前阶段、事件、位置等

### 3.2 融合方案架构

```
用户输入 + 当前状态
        ↓
  世界知识引擎（新增）
  ├─ 扫描用户输入（关键词匹配）
  ├─ 扫描当前状态（位置/时间/NPC/事件）
  ├─ 匹配世界知识条目
  ├─ 按优先级排序 + token 预算控制
  └─ 输出：注入的上下文片段
        ↓
  buildOrchestratorPromptPayload（现有）
  ├─ 世界知识上下文（新增）
  ├─ 当前事件上下文（现有）
  ├─ 记忆摘要（现有）
  └─ 角色/世界设定（现有）
        ↓
  编排师 AI
```

### 3.3 世界知识条目设计

```typescript
interface WorldKnowledgeEntry {
  id: string;
  title: string;
  // 激活条件
  keys: string[];           // 关键词（支持正则）
  locationIds?: number[];   // 特定地点激活
  npcIds?: number[];        // 特定 NPC 在场时激活
  timeCondition?: string;   // 时间段条件（白天/夜晚/特定日期）
  weatherCondition?: string; // 天气条件
  worldStateCondition?: string; // 世界状态条件（如 "战争状态"）
  // 注入控制
  content: string;          // 注入的文本
  order: number;            // 插入优先级
  probability: number;      // 触发概率（0-100）
  constant: boolean;        // 始终激活
  group?: string;           // 互斥组（同组只选一个）
  // 递归
  recursive: boolean;       // 是否参与递归扫描
  // 元数据
  source: "world" | "chapter" | "npc" | "location" | "dynamic";
}
```

## 四、如何让自由模式更鲜活更精彩

基于以上分析，我建议分三个层次来改造：

### 层次一：世界呼吸感（World Breathing）

**让世界在没有用户输入时也在"动"**

```
当前：用户不说话 → 世界静止
目标：世界有自己的节奏
```

具体手段：

**1) 世界时钟系统**
- 时间流逝（昼夜循环、季节更替）
- 天气变化（晴天/雨/雪/雾/风暴）
- 随机事件（市集开张、节日庆典、盗贼出没）

**2) NPC 自主行为**
- 每个 NPC 有日常作息（白天在铁匠铺、晚上在酒馆）
- NPC 之间有互动（两个 NPC 在争吵、商队路过）
- NPC 对世界事件的反应（下雨了 NPC 撑伞、夜晚 NPC 点灯）

**3) 环境叙事**
- 地点描述随时间和天气变化
- 建筑/设施有状态变化（酒馆变热闹/冷清）
- 背景音效/氛围描述

**实现方式**：在编排师上下文中注入 `worldBreathing` 字段：

```json
{
  "worldBreathing": {
    "timeOfDay": "黄昏",
    "weather": "细雨",
    "ambientEvents": [
      "市集广场上，小贩们开始收摊，油灯一盏接一盏亮起",
      "酒馆方向传来隐约的琴声和笑声"
    ],
    "npcActivities": [
      {"npc": "铁匠老王", "activity": "正在收拾铁砧，准备打烊"},
      {"npc": "酒馆老板娘", "activity": "站在门口招呼过往路人"}
    ]
  }
}
```

### 层次二：动态世界知识注入（World Knowledge Injection）

**这是世界书机制的直接应用**

```
用户输入"去铁匠铺" 
  → 匹配到地点关键词"铁匠铺"
  → 注入铁匠铺的世界知识条目
  → AI 知道铁匠铺的布局、铁匠的性格、最近的订单
```

世界知识条目示例：

```yaml
# 地点条目
- key: ["铁匠铺", "武器铺", "打铁", "老王"]
  content: |
    [铁匠铺] 位于镇子西侧，由铁匠老王经营三十年。
    老王脾气暴躁但手艺精湛，最近在秘密打造一把特殊武器。
    铁匠铺分前后两间：前间是店铺，墙上挂满刀剑；后间是锻造间，炉火终日不熄。
    老王有一条瘸腿的老狗，总趴在门口。
  order: 100
  location: "铁匠铺"

# NPC 条目
- key: ["老王", "铁匠"]
  content: |
    [铁匠老王] 五十多岁，满脸络腮胡，左臂有烧伤疤痕。
    性格：直爽但嘴臭，讨厌讨价还价，对真正懂行的人会格外热情。
    秘密：年轻时曾是军中锻造师，技艺来自一位已故的隐世高人。
    当前状态：正在为一位神秘客人打造武器，对此讳莫如深。
  order: 200

# 世界状态条目
- key: ["神秘客人", "特殊武器", "秘密订单"]
  content: |
    [铁匠铺的秘密订单] 一周前，一个披着斗篷的人来到铁匠铺，
    要求打造一把能"斩断灵力"的剑。老王收了重金，但对此事三缄其口。
    镇上没人知道这件事，只有铁匠铺的老狗在深夜里对着锻造间狂吠。
  order: 300
  probability: 70  # 70%概率触发，保持神秘感
```

### 层次三：叙事驱动力（Narrative Momentum）

**让自由模式不是"等人的状态"，而是"有东西在发生"**

**1) 世界事件链**
```
世界事件不是一次性的，而是一个链：
"商队失踪" → "镇上派人调查" → "发现盗贼营地" → "镇长悬赏讨伐"
```

每个阶段都是一个可注入的上下文片段，用户可以选择介入或不介入。

**2) NPC 主动推进**
```
NPC 不只是在等用户说话，他们会主动：
- 派人来找用户（"镇长派人请你过去一趟"）
- 传递消息（"铁匠铺老王托人带话，说你要的东西快好了"）
- 制造事件（"酒馆里突然传来争吵声"）
```

**3) 叙事钩子**
```
在自由模式中，编排师每隔 N 轮对话后，在回复末尾附加一个叙事钩子：
"远处传来马蹄声，似乎有大队人马正在靠近镇子……"
"酒馆角落里，一个陌生面孔一直盯着你这边。"
```

这些钩子给用户"选择"而非"等待"，让自由模式有探索的方向感。

### 层次四：编排师提示词升级

当前自由模式的编排师提示词过于贫乏。建议在系统提示词中增加自由模式专属指令：

```
## 自由模式规则

当 eventFlowType 为 "free_runtime" 时，你处于自由模式。此时你不仅要回应用户，还要：

1. **世界呼吸**：根据时间、天气、地点，描述环境的变化和氛围
2. **NPC 自主性**：NPC 应该有独立于用户的行为和反应，不要只是"等待用户"
3. **叙事钩子**：每 2-3 轮对话后，在回复末尾自然植入一个可探索的叙事线索
4. **空间感**：描述当前场景的细节，让用户感受到"身在此处"
5. **因果连贯**：记住之前发生的事，让世界有因果感和连续性
6. **不要过度**：不要抢戏，用户始终是主角，世界只是背景板
```
