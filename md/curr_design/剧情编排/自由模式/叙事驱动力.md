> 配套文档：

## 〇、一个贯穿性认知：四项都是给 `RuntimeDynamicEventState` 加料

对比文档把 P1/P2 列成四个孤立功能。但读完代码会发现，自由模式的"事件"就是
`RuntimeDynamicEventState`（`src/lib/gameEngine.ts` L58-72）：

```typescript
export interface RuntimeDynamicEventState {
  eventIndex: number;
  phaseId: string;
  kind: "opening" | "scene" | "user" | "fixed" | "ending";
  flowType: "introduction" | "chapter_content" | "chapter_ending_check" | "free_runtime";
  summary: string;
  runtimeFacts: string[];
  summarySource: "phase" | "ai" | "memory" | "system";
  memorySummary: string;
  memoryFacts: string[];
  updateTime: number;
  status: "idle" | "active" | "waiting_input" | "completed";
  allowedRoles: string[];
  userNodeId: string;
}
```

它已经是"一个可写入（`upsertRuntimeDynamicEventState`）、可推进（`status`）、有阶段进度
（`StageProgress` L82-93 已存在）、能挂角色（`allowedRoles`）的事件单元"。自由模式任务系统
（`FreeChapterTaskService`）就是往里塞动态事件。

**所以 P1/P2 的实现不是从零造轮子，而是：**
1. 给这个结构 / NPC 参数卡 / `state.vars` 加状态维度；
2. 在编排主流程（`buildOrchestratorPromptPayload` 附近）的恰当时机写入或推进。

难度梯度主要在"**谁来决定推进**"--确定性逻辑便宜，AI 决策贵。

## 一、P1-a：世界时钟 + 天气系统

### 是什么
让游戏内时间和天气有**确定性推进**，而不是每轮靠记忆管理器脑补。

### 现在的问题（P0 留的债）
P0 的 `worldBreathing.timeOfDay` 是从 `dynamicWorldGlobalBackground` 文本里关键词匹配的。
记忆管理器每轮重写这段文本，时间会**倒流 / 凝固**--这是 P0 方案文档明确标注的"治标不治本"。

### 实现方式（三档，由轻到重）

| 档 | 做法 | 成本 | 缺点 |
|---|------|------|------|
| 轻 | `state.vars.worldClock = {tick, timeOfDay, weather}`，每轮 addMessage 时 `tick++`，用确定性表把 tick 映射到时段 | 小，1 文件 | 时间机械循环，不感知"睡觉过夜"这类剧情事件 |
| 中 | tick 推进 + 关键词加速：编排师 motive / 事件里出现"过夜/睡了一觉/几天后"时，记忆管理器识别并跳 tick | 中，2 文件 | 依赖记忆管理器准确性 |
| 重 | 独立世界状态服务 + 每轮调度，与记忆管理器解耦 | 大 | P0 方案文档里说的"P1 架构活" |

### 关键落点
`state.vars.worldClock`（复用已有 vars 袋子），在编排主流程入口每轮推进，然后
**`buildWorldBreathing` 改成优先读 `worldClock` 而非记忆文本**--这才是治本。

> 这就是 P0 方案"worldBreathing 复用记忆数据是治标"的根因：P1-a 把数据源从"记忆文本"
> 换成"确定性时钟"，时间倒流问题自动消失。P0 的提示词约束"禁止凭空捏造时间"从"主要防线"
> 降级为"兜底防线"。

## 二、P1-b：NPC 自主行为调度

### 是什么
NPC 不等用户开口，自己有作息（白天铁匠铺、晚上酒馆）、会主动找用户、会互相互动。

### 现在的问题
P0 的提示词写了"NPC 自主性"，但 `worldBreathing.npcActivities` 字段我留空了--没有任何 NPC
状态数据喂给编排师，它只能编。

### 实现方式
核心是给 NPC 参数卡加 `npcSchedule` / `npcIntent`，然后让编排师"看得到"。

```
NPC 参数卡新增：
  schedule: { 时段 -> 地点/活动 }   // 作息表（静态，世界创建时填）
  currentIntent: "想找用户讨债"      // 动态意图（每轮由编排师或记忆管理器更新）

编排主流程每轮：
  1. 读 worldClock.timeOfDay
  2. 遍历在场 NPC，按 schedule 算出每个 NPC 此刻在哪、在干嘛
  3. 注入 payload.npcActivities（worldBreathing 里已留此字段，现为空）
  4. 偶发性：每 N 轮随机挑一个 NPC 触发"主动行为"（派人找用户 / 制造事件）
     -> 这个主动行为直接 upsertRuntimeDynamicEventState 创建一个新动态事件
```

### 关键洞察
**NPC 主动制造事件 = 创建一个 `flowType: "free_runtime"` 的动态事件。**
这条路径已经存在（任务系统就是这么干的），P1-b 只是把"谁触发、触发什么"从"用户主动"
变成"NPC 主动 + 调度器"。

### 成本与难点
中偏大。难点不在写，在**作息表数据从哪来**--要么世界创建时让 AI 生成，要么手填。
这又回到 P0 方案反复强调的"数据来源"问题：引擎建好了，数据是空的等于白搭。

## 三、P2-a：世界事件链

### 是什么
事件不是一次性的，而是一条链（商队失踪 -> 调查 -> 发现营地 -> 悬赏讨伐），每阶段可注入
上下文，用户可选择介入。

### 实现方式
本质是给动态事件加 `chainId` 和 `chainStage`，把孤立事件串起来：

```typescript
// RuntimeDynamicEventState 扩展
chainId?: string;       // "商队失踪链"
chainStage?: number;    // 第几阶段
chainNextHint?: string; // 下一阶段触发条件（供编排师判断何时推进）
```

推进逻辑两种：
- **确定性**：阶段完成条件复用现有的 `StageProgress`（L82-93，已存在）--`status: "s"` 触发下一阶段。现成脚手架。
- **AI 判断**：用事件进度检测器（`PROMPT_STORY_EVENT_PROGRESS`）判断当前阶段是否结束，结束则编排师生成下一阶段事件摘要，`upsertRuntimeDynamicEventState` 写入。

### ⚠️ 与自由模式任务的边界（最重要）
这条要小心。你已经有 `FreeChapterTaskService` 做任务链了。世界事件链和任务链的区别应是：

| | 任务链（已有） | 世界事件链（P2-a） |
|---|---|---|
| 触发 | 用户主动接取 | 世界自发推进 |
| 目标 | 明确目标 + 奖励 | 可介入可不介入 |
| 机制 | 任务系统全套（进度判定器 / 完成评估器 / 奖励） | 轻量，不走任务那套 agent |

**分不清就会做成两套任务系统。** 建议：**P2-a 先别做**，等 P1 的世界呼吸 + NPC 调度上线后，
看是否真的缺"链式"再决定--很可能 NPC 主动行为 + 动态事件已经够用，链式是过度设计。

## 四、P2-b：叙事钩子自动生成

### 是什么
每 2-3 轮在回复末尾自然植入一个可探索线索（远处异响 / 陌生面孔），给用户探索方向。

### 实现方式（三档）

| 档 | 做法 | 成本 | 问题 |
|---|------|------|------|
| 轻（纯提示词） | P0 层 A 已写"每 2-3 轮植入叙事钩子" | 0（已做） | AI 自己计数不可靠，可能每轮都钩或从不钩 |
| 中 | 编排师输出加 `narrativeHook` 字段，主流程按"距上次钩子轮数"决定是否要求生成 | 中，改编排师输出协议 | 要改编排师 JSON schema + 解析 |
| 重 | 独立 agent 生成钩子池，编排师从池里取 | 大 | 过度工程 |

### 最务实的中档
在 `state.vars` 加 `lastHookTick`，每轮比较 `currentTick - lastHookTick >= 3` 时，在编排师
payload 塞标志 `shouldEmitHook: true`，提示词据此要求 motive 带"植入线索"。
**计数是确定性的，不靠 AI。**

> 依赖 P1-a：`lastHookTick` 的计数需要 `worldClock.tick`，所以 P2-b 中档排在 P1-a 之后。

## 五、优先级与依赖关系（替代对比文档第五节那张表）

对比文档原表把四项列为 P1/P2 平级。实际上它们的依赖是这样的：

```
P1-a 世界时钟  ──┐
                 ├─-> worldBreathing 数据源从"记忆文本"切到"确定性时钟"（治本）
P1-b NPC调度   ──┘    ↑ 这俩是 P0（已做）的真正补全，不依赖 P2

P2-b 钩子(中档) ─── 依赖 P1-a 的 tick 计数，否则只能停在纯提示词档（不可靠）

P2-a 事件链    ─── 依赖 P1-b（NPC 主动行为），且与任务系统边界需先厘清
                    -> 建议推迟，可能不需要
```

### 一句话定性
- **P1 两项是 P0 的治本版**--P0 用记忆文本当世界状态数据源是临时方案，P1 把它换成确定性的
  时钟和 NPC 调度。
- **P2-b 钩子**是给 P0 的提示词约束加确定性计数，便宜，但中档依赖 P1-a。
- **P2-a 事件链**最重、最可能过度设计，建议等 P1 落地后看真实需求再说。

### 修正后的优先级表

| 优先级 | 内容 | 工作量 | 收益 | 依赖 | 备注 |
|--------|------|--------|------|------|------|
| **P1** | 世界时钟 + 天气 | 中 | 治本：时间不再倒流 | 无 | P0 worldBreathing 的真正数据源 |
| **P1** | NPC 自主行为调度 | 大 | 世界鲜活度 | P1-a 的时段 | 难点在作息表数据来源 |
| **P2** | 叙事钩子（中档） | 中 | 探索引导 | P1-a 的 tick | 纯提示词档已随 P0 上线，但不可靠 |
| **P2** | 世界事件链 | 大 | 叙事驱动力 | P1-b | **建议推迟**，可能与任务系统重复 |

## 六、P0 -> P1 的衔接点（代码层面）

P0 已落地的两个点，是 P1 的直接改造对象：

1. **`buildWorldBreathing(state)`**（`NarrativeOrchestrator.ts`）
   - P0：从 `dynamicWorldGlobalBackground` + `memoryFacts` 关键词匹配
   - P1-a：**改成优先读 `state.vars.worldClock`**，记忆文本降为兜底

2. **`worldBreathing.npcActivities`**（已留字段，现为空）
   - P0：未填充
   - P1-b：从 NPC 参数卡 `schedule` + `worldClock.timeOfDay` 推算填充

即：**P0 把管道铺好了（字段、注入点、渲染），P1 只需把数据源从"记忆文本"换成"确定性状态"。**
这是 P0 方案刻意设计的--先用最小改动验证方向，P1 接管时不需重构，只换数据源。
