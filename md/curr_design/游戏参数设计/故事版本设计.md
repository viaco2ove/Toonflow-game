## 也就是故事发布没有版本号信息？有没有发布日期信息？contentVersion  是发布故事时的故事数据， 还是游玩时的存档数据

数据库字段汇总：

| 表 | 字段 | 说明 |
|---|---|---|
| `t_storyWorld` | `publishStatus` | published / draft |
| `t_storyWorld` | `updateTime` | 最后修改时间 |
| `t_storyChapter` | `updateTime` | 最后修改时间 |

**结论**：
- **没有版本号**，只有 `updateTime`（最后修改时间戳）
- **没有发布日期**
- `contentVersion` 是**游玩时**的快照 hash，记录的是"session 创建那一刻的故事版本"

所以系统目前是**单向追踪**：只能知道"这个 session 是什么时候、用什么版本创建的"，但没有"故事第 N 版"的概念。作者发了几个版本、什么时候发的，**都不记录**。

当前隐患
其实比"没有版本号"更危险的是：章节内容是运行时从 t_storyChapter 实时读取的，不是 session 快照里的。所以作者改了章节内容，旧 session 的编排师/发言器会读到新内容，但 session 的进度状态（phaseId、eventIndex）还是旧的。如果作者删了一个 ## 标题或改了事件结构，进度状态就对不上了--静默错位。

完整迁移函数：

```ts
function migrateSessionProgress(
  oldState: SessionState,
  oldChapter: PublishedChapter,
  newChapter: PublishedChapter,
): { state: SessionState; migrationReport: MigrationReport } {
  const oldProgress = oldState.chapterProgress;
  
  // 1. 构建 phase 映射
  const oldPhases = extractPhases(oldChapter.content);  // ["决定", "出发", ...]
  const newPhases = extractPhases(newChapter.content);
  
  const phaseMapping = buildPhaseMapping(oldPhases, newPhases);
  // { "决定": "决定", "出发": "入校", deleted: ["旧删除了"] }
  
  // 2. 迁移 chapterProgress
  const newPhaseId = phaseMapping[oldProgress.phaseId] 
    ?? newPhases[oldProgress.phaseIndex] 
    ?? newPhases[0] 
    ?? oldProgress.phaseId;
  
  const migrationNotes: string[] = [];
  if (!phaseMapping[oldProgress.phaseId] && oldProgress.phaseId) {
    migrationNotes.push(`phase "${oldProgress.phaseId}" 被删除或重命名`);
  }
  
  const migratedProgress = {
    ...oldProgress,
    chapterId: newChapter.id,
    phaseId: newPhaseId,
    phaseIndex: newPhases.indexOf(newPhaseId),
    // completedEvents 里的 phaseId 也做映射
    completedEvents: oldProgress.completedEvents.map(e => {
      if (e.startsWith("phase:")) {
        const oldId = e.slice(6);
        const newId = phaseMapping[oldId] ?? oldId;
        return `phase:${newId}`;
      }
      return e;
    }),
  };
  
  // 3. 迁移 dynamicEvents（更新 phaseId 引用）
  const migratedDynamicEvents = oldState.dynamicEvents.map(ev => {
    if (ev.phaseId && phaseMapping[ev.phaseId]) {
      return { ...ev, phaseId: phaseMapping[ev.phaseId] };
    }
    return ev;
  });
  
  // 4. 过滤 recentEvents（保留引用仍然有效的）
  const validPhaseIds = new Set(newPhases);
  const migratedRecentEvents = oldState.recentEvents.filter(e => 
    !e.phaseId || validPhaseIds.has(e.phaseId)
  );
  
  // 5. 调整 turnState
  const newPhaseIndex = newPhases.indexOf(newPhaseId);
  const migratedTurnState = {
    ...oldState.turnState,
    canPlayerSpeak: true,
    expectedRoleType: "player",
    expectedRole: oldState.player?.name || "用户",
  };
  
  return {
    state: {
      ...oldState,
      chapterId: newChapter.id,
      chapterProgress: migratedProgress,
      dynamicEvents: migratedDynamicEvents,
      recentEvents: migratedRecentEvents,
      turnState: migratedTurnState,
    },
    migrationReport: {
      oldChapterId: oldChapter.id,
      newChapterId: newChapter.id,
      phaseMapping,
      notes: migrationNotes,
      success: true,
    },
  };
}
```

## 问题点
BLOB 方案的真问题不是存储，而是读取路径：

原本：db("t_storyChapter").where({id}) 一次单行查询
改后：db("t_storyWorld_published").where({id}) 查整行 → 解压 gzip → JSON.parse → 在内存里按 chapterId 找
如果不做缓存层，每轮编排都解压一次，CPU 和内存都会爆。建议加一层 PublishedContentCache（session 级内存缓存）。

漏掉的关键场景：migrateSessionProgress 里说"角色属性卡、状态变量原样迁移"，但如果新版删除了某个 NPC 或改了某个变量名，原样迁移会产生悬空引用：

npcs 里有个 李四，新版章节里没有这个 NPC 了 → 编排师读到不存在的角色
flags.questA = true，新版触发的条件改成 questB → 触发器永远不触发

| 阶段 | 改动范围 | 难度 | 工时估算 | 风险点 |
|------|---------|------|---------|--------|

| 风险 | 中 | runtime 改造遗漏某处会静默 bug；存档迁移 phase 映射不全会进度错乱 |
| ROI（完整版 vs 精简版） | 精简版更优 | 砍掉 AI Agent 迁移，工时从 16-23 天降到 9-13 天，收益损失 <10% |

# 下个版本的设计。方向2

集中做"版本感知 + 发布门控的动态更新"。明确取舍：**忽略旧版本的存档稳定需求**——发布新版后，所有在运行的 session 统一切到新版，不再保留旧版让老存档继续玩。换来砍掉多版本累积、砍掉存档迁移、砍掉 BLOB 压缩，大幅降复杂度。

**重要程度** 中
**风险程度** 低-中
**改动范围程度** 中
**功能收益程度** 中

## 核心思路

沿用方向1 的"草稿/发布分离"，但只保留**单版本**：

- 作者在 `t_storyWorld` / `t_storyChapter`（草稿表）上编辑
- 点"发布"时，把草稿快照复制到 `t_storyWorld_published` / `t_storyChapter_published`（发布表），覆盖该故事的上一版
- **runtime 一律改读发布表**，不再实时读草稿表
- session 关联 `worldPublishId`，版本号 `worldVersion` 用于感知"故事已更新"

### 关键修正（相对方向2 初稿）：不砍 content

初稿"砍掉 content、只快照 runtimeOutline"有两个硬伤，必须推翻：

1. **结构与正文割裂**。`runtimeOutline` 本就是从 `content` 解析出来的。冻 outline、放 content，作者改了 `##` 标题顺序后，outline（冻在旧发布）还是旧序，content（live）已是新序，编排师按 outline 取错段落——比现状更别扭（现状至少 outline 与 content 同源一致）。
2. **"省存储"动机不成立**。BLOB/gzip 只在**多版本累积**时才必要。单版本覆盖下 content 不累积，直接当普通 TEXT 列存，查询成本和现状 `db("t_storyChapter").where({ id })` 相同，**不需要方向1 担心的内存缓存层**。砍 content 省下的那点存储，换来的是割裂 bug，不划算。

## 表结构

```
t_storyWorld_published
  id            INTEGER PRIMARY KEY
  worldId       INTEGER   -- 原始草稿世界ID
  version       INTEGER   -- 发布版本号（每次发布 +1，仅用于版本感知）
  publishedAt   INTEGER   -- 发布时间戳
  publishedBy   TEXT      -- 发布者（可选）
  -- world 本身字段（title / settings / playerRole / narratorRole / background 等）整行复制快照
  UNIQUE(worldId)          -- 单版本：一个 worldId 只对应一行
  INDEX(worldId)
```

world 字段也快照进 published（整行复制，不压缩）。理由：`world.settings` 里有预热快照、触发动效配置等运行态数据，不快照则作者改草稿期间运行中 session 仍受影响，违背"发布门控"。

```
t_storyChapter_published
  id              INTEGER PRIMARY KEY
  worldPublishId  INTEGER   -- 关联 t_storyWorld_published.id
  chapterId       INTEGER   -- 原始草稿 chapterId（不变，用于映射）
  title           TEXT      -- 发布时标题快照
  content         TEXT      -- 发布时正文快照（不压缩，直接存）
  runtimeOutline  TEXT      -- 发布时解析后的 phase 结构快照
  sort            INTEGER   -- 发布时章节排序
  publishedAt     INTEGER   -- 发布时间戳
  UNIQUE(worldPublishId, chapterId)
  INDEX(worldPublishId)
```

## 版本感知（沿用方向1 第一步）

```
t_gameSession:
  + worldPublishId  INTEGER   -- 关联 t_storyWorld_published.id
  + worldVersion    INTEGER   -- session 创建/升级时记录的 publishedVersion
```

注意：单版本覆盖下 `worldPublishId` 始终指向同一行（被覆盖更新），**不能用它判断版本**。版本感知靠数值比较 `session.worldVersion` vs `t_storyWorld_published.version`（或 `t_storyWorld.publishedVersion`）：

- 相同 -> 正常继续
- 不同 -> 前端在"聊过"面板对应故事块的"继续"按钮左侧显示"故事已更新"按钮。点击弹框："故事已更新到第 N 版，升级后将切换到新版继续游玩，旧版进度按新版结构对齐（结构变动较大处会就近回退）。"

## 单版本覆盖的取舍（诚实标注）

| 场景 | 方向2（单版本覆盖） | 方向1（多版本） |
|------|------------------|--------------|
| 作者改草稿期间，在运行的 session | ✅ 不受影响（读 published） | ✅ 不受影响 |
| 作者**发布新版**后，在运行的旧 session | ⚠️ 统一切到新版（动态更新） | ✅ 停在旧版，可选升级 |
| 旧 session 升级时进度对齐 | 需处理（见下） | 需处理 |
| 保留历史版本/回滚 | ❌ 不支持 | ✅ 保留全部历史行 |
| 存档迁移（跨结构变动） | ❌ 仅轻量对齐，无迁移缓冲 | 可选硬编码/AI 迁移 |

核心取舍：**放弃"老存档停在旧版"**，换取不维护多版本、不做存档迁移。适合"作者改动以文本微调为主、结构大改前会让玩家重开"的预期。

## 发布后的进度对齐（轻量，非迁移）

单版本覆盖下没有"旧版 vs 新版并存"，所以不需要方向1 的 `migrateSessionProgress`。但发布切换瞬间，session 的 `chapterProgress`（phaseId / eventIndex / completedEvents 等）可能和新 outline 对不上。策略——**尽力对齐，不对齐则回退安全态**：

- phaseId 仍在新 outline 中 -> 直接用，继续
- phaseId 不在新 outline 中 -> 按名称/索引就近匹配最近有效 phase；匹配不到则回退到当前章节第一个 phase，`eventIndex` 清零，turnState 重置为"等待玩家输入"
- completedEvents 里的失效 phaseId 引用 -> 清理
- 不做 AI 推断迁移（方向1 第三步，ROI 低，砍掉）

对齐结果生成轻量"升级说明"返回前端："检测到 phase '苏醒' 已移除，已定位到 '入校' 继续"。

## 开发难度评估

| 阶段 | 改动范围 | 难度 | 工时估算 | 风险点 |
|------|---------|------|---------|--------|
| 版本字段 + 检测 | initDB 加字段、fixDB 迁移、publishWorldSynchronously 加 `version++`、listSession 返回版本对比、前端"故事已更新"按钮 | 低 | 1-2 天 | 低 |
| published 表 + 发布逻辑 | 新建 2 张表、`publishWorldSynchronously` 改为"草稿 -> 复制写 published（覆盖）"、删除故事级联清 published | 中 | 2-3 天 | 低（覆盖语义简单） |
| **runtime 读路径改造** | SessionService/TaskProgressEngine/TriggerEngine/SessionMemoryWorker 等 20+ 处 `db("t_storyChapter")` 改读 `t_storyChapter_published`；world.settings 读 published | 中 | 3-4 天 | 中（遗漏某处没改 -> 静默 bug） |
| 发布后进度对齐 | 轻量对齐函数 + 前端升级说明 UI | 低-中 | 1-2 天 | 低 |

**总计** ≈ 7-11 天。比方向1 精简版（9-13 天）省 2-3 天，主要省在：无多版本累积逻辑、无存档迁移、无 BLOB/缓存层。
