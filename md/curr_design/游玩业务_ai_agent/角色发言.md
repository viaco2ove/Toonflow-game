# 角色发言设计

## 1. 概述

角色发言（Speaker）是 AI 故事系统的输出层，负责将编排结果转化为用户可见的台词。

## 2. 三档发言机制

### 2.1 T0：模板直出

**适用场景**：
- 旁白环境补句
- 万能角色/路人起哄
- 明显功能性推进句
- 已有强规则的阶段过渡句

**特点**：
- 不调用大模型
- 直接根据 `speaker + motive + phase` 用模板拼装
- 目标 50~200ms 内出结果

**示例**：
```
旁白：(练武场的哄笑声仍未停歇，几道目光在你与萧炎之间来回扫动)
某男子：(抱着胳膊冷笑一声) 怎么，不敢接话了？
```

### 2.2 T1：轻量模型

**适用场景**：
- 普通 NPC
- 泛旁白
- 万能角色临演
- 非关键角色的过场发言

**特点**：
- 用低延迟模型
- 严格短上下文
- 目标 1~3 秒

### 2.3 T2：高质量模型

**适用场景**：
- 萧炎、纳兰嫣然、薰儿等关键角色
- 用户首次建立关系
- 关键冲突
- 高价值章节节点

**特点**：
- 允许更高质量
- 允许更长一点的动态上下文
- 目标 3~8 秒

## 3. 当前事件数据结构

角色发言器输入的 `[当前事件]` 需要包含当前阶段的详细信息：

```
[当前事件]
index: 2
kind: scene
flow: chapter_content
status: active
summary: [s]黑术暗影君王的窥探 → [s]旁白引导剧情 → [i]遇见与交流
currStageIndex: 2
currStageSummary: 随机遇见各种NPC，聊天5轮对话后进入下个事件，用户发言5次
facts: 用户在陌生石谷探索，黑雾正在靠近
```

**关键字段说明**：
- `summary`：带状态标记的事件摘要，显示各阶段进度
- `currStageIndex`：当前阶段索引，帮助发言器理解当前所处阶段
- `currStageSummary`：当前阶段的详细摘要，包含阶段要求（如发言次数要求）

## 4. 极简上下文设计

### 4.1 当前问题

当前 speaker 输入仍然会带：
- 世界简介
- 角色参数卡压缩版
- 故事状态摘要
- 最近多轮对话
- 其他可见角色

这对"出一句话"来说仍然偏重。

### 4.2 最小 payload 设计

speaker 只保留五块：
1. 当前说话人最小资料
2. 当前动机
3. 当前阶段标签 + 当前阶段索引 + 当前阶段摘要
4. 最近 2~3 条必要对话
5. 当前用户最新输入

**禁止**：
- 长世界简介
- 长故事背景摘要
- 大段角色参数卡
- 超过 3 条以上最近对话
- 大量"其他可见角色"

## 5. 发言策略路由器

```typescript
type SpeakerModeDecision = {
  mode: "template" | "fast" | "premium";
  voiceMode: "skip" | "async" | "immediate";
  memoryMode: "skip" | "async";
  reason: string;
};
```

- `template`：主要给旁白、万能角色、功能性补句
- `fast`：给普通 NPC 和普通过场
- `premium`：只给关键角色与关键节点

对，就是这个流程：

```
编排师输出 → { currentRole, motive, ... } → 前端接收
    ↓
前端发起台词生成请求 → 把 currentRole + motive 传给后端发言器
    ↓
SpeakerRouteEngine 根据 role + motive 自动判定 fast/premium
    ↓
发言器按档位选模型、选提示词模板、生成台词
```

**编排师负责"谁说话、为什么说"，发言器负责"怎么说"**，中间的 fast/premium 路由是自动的，前端只是透传编排师的输出。

### 判定规则（按优先级从高到低）

| 优先级 | 条件 | mode | reason |
|-------|------|------|--------|
| 1 | 角色标记为**重要角色/关键角色** | premium | `key_role_premium` |
| 2 | **有用户输入** + NPC/旁白需要回应 | premium | `npc_after_user_input` / `narrator_after_user_input` |
| 3 | 动机含**高风险关键词**（告白、诀别、大战、背叛…） | premium | `high_risk_premium` |
| 4 | 旁白 + 无用户输入 + 动机匹配模板模式 | fast | `narrator_fast_replacing_template` |
| 5 | 万能角色 + 无用户输入 + 动机匹配起哄模式 | fast | `wildcard_fast_replacing_template` |
| 6 | 旁白 + 无用户输入 + 动机短或过场类 | fast | `narrator_fast_bridge` |
| 7 | 万能角色 NPC + 无用户输入 | fast | `wildcard_fast_turn` |
| 8 | 普通 NPC + 无用户输入 + 动机短/承接类 | fast | `normal_npc_fast` |
| 9 | 普通 NPC（兜底） | premium | `normal_npc_premium` |
| 10 | 默认兜底 | fast | `default_fast` |

### 核心设计思路

**关键场景用大模型（premium），日常承接用轻量模型（fast）**：

- **premium 触发**：用户刚发了消息（需要高质量回应）、重要角色发言、高风险剧情节点（告白/背叛/生死）
- **fast 触发**：旁白过场、万能角色起哄、短承接轮次、没有用户输入时的日常推进

这个 `SpeakerRouteEngine` 是一个**纯函数路由引擎**，完全基于角色类型 + 动机关键词自动决策，不需要前端传任何模式参数。

## 6. 语音链路

### 6.1 语音不能阻塞正文首屏

正文必须先落。

语音统一分两种：
- `immediate`：当前消息刚落库就异步请求语音
- `deferred`：用户停留时再请求

### 6.2 旁白/万能角色优先走标准音色

因为这类内容本来就是低成本内容：
- 不需要每轮都跑复杂克隆链
- 优先走标准预设音色
- 进一步减少等待

## 7. 验收指标

- T0 模板：<200ms 内返回正文
- T1 轻量：1~3 秒
- T2 高质量：3~8 秒
- 前端长请求误报超时：降到接近 0
- 不出现"角色说错人"
- 不出现"模型代替用户说台词"

"那里来"的直接回答：这两个块的数据源早就存在——t_game_session 表里这条 session 的 state JSON 字段里就有 memoryFacts / memoryTags（你可以直接查库验证），SessionMemoryWorker 每 30 秒往里写。只是 buildSpeakerUserPrompt 组装发言 prompt 时根本没去取这两个字段，所以请求体里没有。数据在库里躺着，prompt 组装函数没拿，这就是"缺"的全部含义。

#### 三个必须避开的坑
1. 不要上向量数据库。 单 story 记忆撑死几千到一两万条，512 维 float32 ≈ 2KB/条 → 万条约 20MB。JS 暴力扫描万条 cosine 约 10~30ms。引 qdrant/milvus/faiss 是给自己加一个运维负担和一条网络链路，收益为零。SQLite BLOB + 内存扫描足够。

2. m3e-small 分不清主谓宾。 "张三打了李四" 和 "李四打了张三" 余弦相似度能到 0.95 以上。所以必须用 subjectId 做硬过滤再算相似度——NPC 只召回 subjectId IN (自己, user, 关系) 的记忆，绝不能全库语义撞。

3. 向量召回必须有硬上限且可丢弃。 建议上限 3 条、预算 200 token。超预算直接丢，绝不能反向挤压 L0/L1。召回失败只能导致"不记得"，不能导致"记错了"——后者才真正摧毁沉浸感。

##### 数据流（对比 P1）

```
P1：写入 → SQL排序（importance DESC, createdAt DESC）→ 8条
P2：写入 → 向量生成(vec列) → 召回(加权分) → top3+200token
          ↓ 失败降级
       P1 SQL 排序兜底
```

**召回公式**：`score = 0.5×cos + 0.3×importance/5 + 0.2×timeDecay`
- `cos`：m3e-small 512d 语义相似度（防串戏靠 subjectId 硬过滤，向量负责语义匹配）
- `importance/5`：结构化重要性权重
- `timeDecay = 0.5^(Δturn/50)`：越近的记忆越重

**recallQueries 来源**：发言时的 `payloadMemoryFacts`（记忆事实句），没有才用 `memorySummary`。

**⚠️ 前置条件**：m3e-small 模型未装好时，`encodeTexts` 会 catch 返回空数组，向量召回全程静默降级到 P1 SQL，不影响主链路。首次写入新事实时向量异步生成（`void`），下次发言才能被向量召回命中。

## t_role_memory 写入时机

**完整链路**：

```
用户发送消息
  → addMessage()
    → scheduleSessionMemoryRefresh()
      → triggerStoryMemoryRefreshInBackground()

              → vectorizeExistingRow()    ← 写入后异步生成向量
```

每轮用户消息触发一次，写入内容是**本轮凝练出的记忆事实句**，按 `detectSubject` 判断归属（事实句含谁的名字就归谁），同一 `storyId + subjectId + content` 去重不重复写。

## 回溯时 t_role_memory 怎么处理

**答案：基于 sourceTurn 过滤。**

回溯机制靠的是 `t_sessionMessage.revisitData`（存 message 发送前/后的 state 快照），回溯时恢复 session state，角色发言走正常流程，`loadRoleMemoriesForSpeaker` 查表时**没有 sourceTurn 过滤**：

```sql
SELECT * FROM t_role_memory
WHERE storyId = ? AND subjectId IN (speakerName, 'user', '')
ORDER BY importance DESC, createdAt DESC
LIMIT 8
```

增加 sourceTurn 过滤

| 方案 | 做法 | 代价 |
|---|---|---|
| **软标记** | 回溯时记录 `revisitTurn`，召回时 `WHERE sourceTurn <= revisitTurn` | 改动召回逻辑 |



用 `lastMessageId`：

| 位置 | 改动 |
|---|---|
| **写入** `SessionService.ts:2336` | `sourceTurn = params.lastMessageId`（全局消息 ID） |
| **读取** `loadRoleMemoriesForSpeaker` | 参数 `currentEventIndex` → `sourceTurnCap`，SQL `WHERE sourceTurn <= sourceTurnCap` |
| **召回** `recallRoleMemories` | 参数 `currentTurn` → `sourceTurnCap`，评分里 `turnDelta = |sourceTurn - cap|` |
| **编排器** `NarrativeOrchestrator.ts` | `input.state.lastMessageId` 传入两处调用 |

## 为什么有效

```
lastMessageId 特性：
  ✓ 全局单调递增（跨 session 不变）
  ✓ 回溯删消息后自动回退（stateJson 恢复时还原）
  ✓ 自由章节也能正常工作（消息照发，ID 照增）
  ✓ 不依赖 chapterId / eventIndex 等结构化概念
```

回溯时 `lastMessageId` 回到旧值 → SQL `WHERE sourceTurn <= 旧值` → 旧分支记忆被过滤 → 新分支发言自然读到新事实。无需任何额外逻辑。

## content 记什么

唯一判据：**一个角色在毫无上下文的情况下读到这句话，能不能明白「我知道了一件什么事」？**

| ✅ 该记 | ❌ 不该记 |

| 赤眉老人答应替白锦儿担保 | 他点了点头 |

# 我们单独做了一个角色记忆表，那么为什么不去向量检索台词。这样做的目的是什么？
问得好，这戳到了设计选择的核心。先加载图表模块。
**一句话：记忆表存的不是「台词」，是「角色知道的事」。** 两者之间隔着一步不可省略的转化。

## 为什么台词不能直接检索

| 问题 | 后果 | 记忆表怎么解决的 |
|---|---|---|
| **权限：谁该知道** | 张三对李四的悄悄话，王五的发言器也会检索到 → **串戏**。向量检索是无差别语义匹配，它不知道"这个角色有没有资格知道" | 查询前先 `subjectId IN (说话人, user, __world__)` 硬过滤。**这是台词做不到的** |
| **指代：这句话在说谁** | "他把那个东西给我了" —— 脱离上下文后模型不知道是张三给李四，还是反过来 | AI 凝练时已完成指代消解，写进去就是完整句子 |
| **模型缺陷：分不清主谓宾** | 已验证 m3e-small 对「张三打了李四」和「李四打了张三」余弦相似度 > 0.95 —— 检索回来的可能**正好是反的** | 先用 `subjectId` 过滤再算相似度，把可能搞错的范围缩到最小 |
| **粒度与成本** | 单 story 台词几千~万条，全量 embedding + 检索回来大段原文，token 吃不消 | 一行 ≤80 字，召回硬上限 3 条 / 200 token |

前两条是**硬伤** —— 不是精度问题，是会直接产出错误信息。第三条尤其危险：模型会把"李四打了张三"当背景喂给角色，而且没有任何报错。

## 但你的直觉有一半是对的

台词检索**有价值**，只是不能替代记忆表 —— 它是不同层的东西：

| 层 | 数据源 | 回答的问题 |
|---|---|---|
| L1 短期 | 最近 12 条台词原文 | 刚才说到哪了 |
| L2 长期（现在做的） | `t_role_memory` | **这个角色记得什么事** |
| L3 场景细节（缺） | 台词向量 | 当时**原话**是怎么说的 |

L3 缺了会怎样：角色记得"张三答应替我担保"，但找不回"那天在破庙里他是怎么说的"。**记忆是骨架，台词是血肉。**

## 要做 L3 的话，三条约束不能少

1. **检索到的台词必须连同上下文窗口一起返回** —— 单独一句全是"他""那个东西"，等于白召回
2. **先用可见性过滤，再算相似度** —— 台词表得按 speaker / 场景在场角色先做 SQL 硬过滤
3. **上限卡死 3 条 / 200 token** —— 召回失败只能"不记得"，绝不能反向挤压 L0/L1 的预算

这三条守住的话，L3 是可以做的，而且 `localEmbed` 的基础设施（`encodeTexts` + `cosineScore`）已经现成。
