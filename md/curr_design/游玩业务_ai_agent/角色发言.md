# 角色发言设计

## 1. 概述

角色发言（Speaker）是 AI 故事系统的输出层，负责将编排结果转化为用户可见的台词。

## 2. 三档发言机制

### 2.1 T0：模板直出

**适用场景**：
- 旁白环境补句
- 万能角色/路人起哄
- 明显功能性推进句
- 已有强规则的阶段过渡句

**特点**：
- 不调用大模型
- 直接根据 `speaker + motive + phase` 用模板拼装
- 目标 50~200ms 内出结果

**示例**：
```
旁白：(练武场的哄笑声仍未停歇，几道目光在你与萧炎之间来回扫动)
某男子：(抱着胳膊冷笑一声) 怎么，不敢接话了？
```

### 2.2 T1：轻量模型

**适用场景**：
- 普通 NPC
- 泛旁白
- 万能角色临演
- 非关键角色的过场发言

**特点**：
- 用低延迟模型
- 严格短上下文
- 目标 1~3 秒

### 2.3 T2：高质量模型

**适用场景**：
- 萧炎、纳兰嫣然、薰儿等关键角色
- 用户首次建立关系
- 关键冲突
- 高价值章节节点

**特点**：
- 允许更高质量
- 允许更长一点的动态上下文
- 目标 3~8 秒

## 3. 当前事件数据结构

角色发言器输入的 `[当前事件]` 需要包含当前阶段的详细信息：

```
[当前事件]
index: 2
kind: scene
flow: chapter_content
status: active
summary: [s]黑术暗影君王的窥探 → [s]旁白引导剧情 → [i]遇见与交流
currStageIndex: 2
currStageSummary: 随机遇见各种NPC，聊天5轮对话后进入下个事件，用户发言5次
facts: 用户在陌生石谷探索，黑雾正在靠近
```

**关键字段说明**：
- `summary`：带状态标记的事件摘要，显示各阶段进度
- `currStageIndex`：当前阶段索引，帮助发言器理解当前所处阶段
- `currStageSummary`：当前阶段的详细摘要，包含阶段要求（如发言次数要求）

## 4. 极简上下文设计

### 4.1 当前问题

当前 speaker 输入仍然会带：
- 世界简介
- 角色参数卡压缩版
- 故事状态摘要
- 最近多轮对话
- 其他可见角色

这对"出一句话"来说仍然偏重。

### 4.2 最小 payload 设计

speaker 只保留五块：
1. 当前说话人最小资料
2. 当前动机
3. 当前阶段标签 + 当前阶段索引 + 当前阶段摘要
4. 最近 2~3 条必要对话
5. 当前用户最新输入

**禁止**：
- 长世界简介
- 长故事背景摘要
- 大段角色参数卡
- 超过 3 条以上最近对话
- 大量"其他可见角色"

## 5. 发言策略路由器

```typescript
type SpeakerModeDecision = {
  mode: "template" | "fast" | "premium";
  voiceMode: "skip" | "async" | "immediate";
  memoryMode: "skip" | "async";
  reason: string;
};
```

- `template`：主要给旁白、万能角色、功能性补句
- `fast`：给普通 NPC 和普通过场
- `premium`：只给关键角色与关键节点

对，就是这个流程：

```
编排师输出 → { currentRole, motive, ... } → 前端接收
    ↓
前端发起台词生成请求 → 把 currentRole + motive 传给后端发言器
    ↓
SpeakerRouteEngine 根据 role + motive 自动判定 fast/premium
    ↓
发言器按档位选模型、选提示词模板、生成台词
```

**编排师负责"谁说话、为什么说"，发言器负责"怎么说"**，中间的 fast/premium 路由是自动的，前端只是透传编排师的输出。

### 判定规则（按优先级从高到低）

| 优先级 | 条件 | mode | reason |
|-------|------|------|--------|
| 1 | 角色标记为**重要角色/关键角色** | premium | `key_role_premium` |
| 2 | **有用户输入** + NPC/旁白需要回应 | premium | `npc_after_user_input` / `narrator_after_user_input` |
| 3 | 动机含**高风险关键词**（告白、诀别、大战、背叛…） | premium | `high_risk_premium` |
| 4 | 旁白 + 无用户输入 + 动机匹配模板模式 | fast | `narrator_fast_replacing_template` |
| 5 | 万能角色 + 无用户输入 + 动机匹配起哄模式 | fast | `wildcard_fast_replacing_template` |
| 6 | 旁白 + 无用户输入 + 动机短或过场类 | fast | `narrator_fast_bridge` |
| 7 | 万能角色 NPC + 无用户输入 | fast | `wildcard_fast_turn` |
| 8 | 普通 NPC + 无用户输入 + 动机短/承接类 | fast | `normal_npc_fast` |
| 9 | 普通 NPC（兜底） | premium | `normal_npc_premium` |
| 10 | 默认兜底 | fast | `default_fast` |

### 核心设计思路

**关键场景用大模型（premium），日常承接用轻量模型（fast）**：

- **premium 触发**：用户刚发了消息（需要高质量回应）、重要角色发言、高风险剧情节点（告白/背叛/生死）
- **fast 触发**：旁白过场、万能角色起哄、短承接轮次、没有用户输入时的日常推进

这个 `SpeakerRouteEngine` 是一个**纯函数路由引擎**，完全基于角色类型 + 动机关键词自动决策，不需要前端传任何模式参数。

## 6. 语音链路

### 6.1 语音不能阻塞正文首屏

正文必须先落。

语音统一分两种：
- `immediate`：当前消息刚落库就异步请求语音
- `deferred`：用户停留时再请求

### 6.2 旁白/万能角色优先走标准音色

因为这类内容本来就是低成本内容：
- 不需要每轮都跑复杂克隆链
- 优先走标准预设音色
- 进一步减少等待

## 7. 验收指标

- T0 模板：<200ms 内返回正文
- T1 轻量：1~3 秒
- T2 高质量：3~8 秒
- 前端长请求误报超时：降到接近 0
- 不出现"角色说错人"
- 不出现"模型代替用户说台词"

"那里来"的直接回答：这两个块的数据源早就存在——t_game_session 表里这条 session 的 state JSON 字段里就有 memoryFacts / memoryTags（你可以直接查库验证），SessionMemoryWorker 每 30 秒往里写。只是 buildSpeakerUserPrompt 组装发言 prompt 时根本没去取这两个字段，所以请求体里没有。数据在库里躺着，prompt 组装函数没拿，这就是"缺"的全部含义。

#### 三个必须避开的坑
1. 不要上向量数据库。 单 story 记忆撑死几千到一两万条，512 维 float32 ≈ 2KB/条 → 万条约 20MB。JS 暴力扫描万条 cosine 约 10~30ms。引 qdrant/milvus/faiss 是给自己加一个运维负担和一条网络链路，收益为零。SQLite BLOB + 内存扫描足够。

2. m3e-small 分不清主谓宾。 "张三打了李四" 和 "李四打了张三" 余弦相似度能到 0.95 以上。所以必须用 subjectId 做硬过滤再算相似度——NPC 只召回 subjectId IN (自己, user, 关系) 的记忆，绝不能全库语义撞。

3. 向量召回必须有硬上限且可丢弃。 建议上限 3 条、预算 200 token。超预算直接丢，绝不能反向挤压 L0/L1。召回失败只能导致"不记得"，不能导致"记错了"——后者才真正摧毁沉浸感。

## 三阶段请求体对比

| 阶段 | 请求体新增块 | 内容来源 | 每块预算 |
|---|---|---|---|

## P1 做完，请求体会长这样

在现有 `[角色记忆事实]` 后面多一块**按角色隔离**的记忆：

```
[角色记忆事实]        ← P0 已有：全组共用一本账，12条硬截断
1. 林凡残影称塔内有人主导吞噬
2. 用户答应帮小满找灯
...

[角色专属记忆]        ← P1 新增：只有"陈曦"自己的账
【关于自己】陈曦曾在第三章目击林凡进入塔内，未告知任何人
【关于用户】用户两次试探陈曦是否知情，陈曦均装傻
【关系】陈曦与林凡是旧识，刻意隐瞒
```

**P1 解决 P0 的两个死穴**：

| P0 的问题 | P1 怎么修 |
|---|---|
| 12 条硬截断，旧的被新事实挤出去 | 表无上限，按 `importance + 时间衰减` 打分取前排 |
| 所有 NPC 翻**同一本**账——张三的隐私李四也看得到 | `subjectId` 过滤：陈曦只看到"自己/用户/关系"三类 |

注意：P1 的块和 P0 的块**内容会重叠**（表里的数据源头也是 SessionMemoryWorker 凝练的），所以 P1 稳定后，P0 那块可以收窄甚至撤掉，总量不涨。

## P2 做完，请求体再多的东西

发言器请求体最后多一块**从很旧的章节按"意思"捞回来的事**：

```
[久远记忆召回]        ← P2 新增：跨章节、语义相似
1. (第1章·相似度0.82) 用户曾对林凡说过"我小时候差点淹死"
2. (第2章·相似度0.78) 塔的底层有水声，林凡当时脸色变了
```

同时**编排师的响应体**多一个字段（这是 P2 的关键设计，省一次 LLM 调用）：

```json
// 编排师出参（runNarrativePlan 的结果）
{
  "motive": "...",
  "recallQueries": ["用户怕水", "塔内水声与林凡的反应"]   ← 新增
}
```

发言器拿 `recallQueries` 去查向量，**不为检索单独调一次 LLM**（省 300~800ms）。编排师请求体只多一句指令要求它输出这个字段。

## 三个块的位置和纪律

全部插在 `[剧情摘要]` 之后、`[最近对话]` 之前，且**有内容才出现**：

- P1 无数据（新角色）→ 块不出现，token 不浪费
- P2 召回为空或超预算 → 直接丢，**只能导致"不记得"，不能导致"记错了"**
- compactMode（快速发言）下：P1 砍到 4 条，P2 直接关闭

**一句话**：P0 是"给全组一本共用笔记"（已上线）；P1 是"每人一本私人笔记"；P2 是"配一个按意思翻旧账的功能"。请求体上就是从 1 个记忆块变成最多 3 个，总预算控制在 900 token 以内。

防串戏：陈曦只查到 subjectId IN (陈曦, 'user', '') 的记忆——张三的秘密不会被李四读到

####  P2 做了什么

| 文件 | 改动 |
|---|---|
| `src/migrations/20260910_000001_add_role_memory_vec_column.js` | 新建：加 `vec VARBINARY(2048)` 列（m3e-small 512d） |
| `src/lib/localEmbed.ts` | 加 `encodeTexts()` 导出，供召回模块调用 |
| `src/modules/game-runtime/services/RoleMemoryService.ts` | 加 `recallRoleMemories()` + `vectorizeExistingRow()`；写入时自动向量化 |
| `src/modules/game-runtime/engines/NarrativeOrchestrator.ts` | payload 整体 async，接入向量召回，降级链：recall → SQL |

##### 数据流（对比 P1）

```
P1：写入 → SQL排序（importance DESC, createdAt DESC）→ 8条
P2：写入 → 向量生成(vec列) → 召回(加权分) → top3+200token
          ↓ 失败降级
       P1 SQL 排序兜底
```

**召回公式**：`score = 0.5×cos + 0.3×importance/5 + 0.2×timeDecay`
- `cos`：m3e-small 512d 语义相似度（防串戏靠 subjectId 硬过滤，向量负责语义匹配）
- `importance/5`：结构化重要性权重
- `timeDecay = 0.5^(Δturn/50)`：越近的记忆越重

**recallQueries 来源**：发言时的 `payloadMemoryFacts`（记忆事实句），没有才用 `memorySummary`。

**⚠️ 前置条件**：m3e-small 模型未装好时，`encodeTexts` 会 catch 返回空数组，向量召回全程静默降级到 P1 SQL，不影响主链路。首次写入新事实时向量异步生成（`void`），下次发言才能被向量召回命中。

## t_role_memory 的数据是什么时候增加，台词回溯又会做什么处理
